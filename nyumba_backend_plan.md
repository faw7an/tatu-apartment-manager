## 1. Architecture Overview

```
┌─────────────────────────────────────────────────────┐
│                   Hetzner VPS                        │
│                                                      │
│  ┌──────────┐   ┌──────────────┐   ┌─────────────┐  │
│  │  Nginx   │──▶│  Express API │──▶│  PostgreSQL │  │
│  │ :80/:443 │   │   :3000      │   │   :5432     │  │
│  └──────────┘   └──────────────┘   └─────────────┘  │
│       │                │                             │
│       │         ┌──────┴──────┐                      │
│       │         │   /storage  │                      │
│       │         │  (PDFs)     │                      │
│  Download       └─────────────┘                      │
│  Page + PWA                                          │
│  (/var/www)                                          │
└─────────────────────────────────────────────────────┘

All 4 services run as Docker containers.
PostgreSQL data lives in a named Docker volume → fully portable.
```

**Key decisions:**
- One apartment per deployment — no multi-tenancy complexity
- `MPESA_SIMULATE=true` in `.env` to use fake payments during dev/testing
- Receipts are PDFs generated by Puppeteer and stored in `/storage/receipts/`
- Excel reports generated on-demand by ExcelJS — not stored, streamed to client
- All scheduled jobs run inside the Express container using `node-cron`
- Nginx handles SSL termination (Let's Encrypt) and serves the static download page

## 2. Docker & Container Design

### Containers

| Container | Image | Port | Purpose |
|---|---|---|---|
| `nyumba-api` | Custom (Node 20 Alpine) | 3000 | Express API |
| `nyumba-db` | postgres:16-alpine | 5432 | PostgreSQL database |
| `nyumba-nginx` | nginx:alpine | 80, 443 | Reverse proxy + SSL + static files |
| `nyumba-certbot` | certbot/certbot | — | SSL cert renewal (runs once + cron) |

### docker-compose.yml structure

```yaml
services:

  api:
    build: .
    container_name: nyumba-api
    restart: always
    env_file: .env
    ports:
      - "3000:3000"
    volumes:
      - ./storage:/app/storage        # PDF receipts persisted
    depends_on:
      db:
        condition: service_healthy    # wait for postgres to be ready
    networks:
      - nyumba-net

  db:
    image: postgres:16-alpine
    container_name: nyumba-db
    restart: always
    env_file: .env                    # reads POSTGRES_* vars
    volumes:
      - pgdata:/var/lib/postgresql/data   # named volume = portable
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U nyumba"]
      interval: 5s
      timeout: 5s
      retries: 5
    networks:
      - nyumba-net

  nginx:
    image: nginx:alpine
    container_name: nyumba-nginx
    restart: always
    ports:
      - "80:80"
      - "443:443"
    volumes:
      - ./nginx/nginx.conf:/etc/nginx/nginx.conf:ro
      - ./certbot/conf:/etc/letsencrypt:ro
      - ./certbot/www:/var/www/certbot:ro
      - ./www:/var/www/html:ro          # download page + Flutter PWA
    depends_on:
      - api
    networks:
      - nyumba-net

  certbot:
    image: certbot/certbot
    volumes:
      - ./certbot/conf:/etc/letsencrypt
      - ./certbot/www:/var/www/certbot
    # Run manually: docker compose run certbot certonly ...

volumes:
  pgdata:                              # survives container restarts + rebuilds

networks:
  nyumba-net:
    driver: bridge
```

### Why a named volume for PostgreSQL

```
pgdata volume lives on the host filesystem at:
/var/lib/docker/volumes/nyumba_pgdata/_data

This means:
✅ docker compose down     → data survives
✅ docker compose up       → data comes back
✅ docker compose pull     → data survives image updates
✅ tar the volume dir      → full DB backup
✅ copy to new server      → portable deployment
```

### Portability — moving to a new server

```bash
# On old server — backup
docker exec nyumba-db pg_dump -U nyumba nyumba > backup.sql

# On new server — restore
docker compose up -d db
docker exec -i nyumba-db psql -U nyumba nyumba < backup.sql
docker compose up -d
```

### Dockerfile (API)

```dockerfile
FROM node:20-alpine

# Puppeteer deps (for PDF generation)
RUN apk add --no-cache chromium nss freetype harfbuzz ca-certificates ttf-freefont

ENV PUPPETEER_SKIP_CHROMIUM_DOWNLOAD=true
ENV PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium-browser

WORKDIR /app

COPY package*.json ./
RUN npm ci --only=production

COPY . .
RUN npm run build

# Create storage dir for PDFs
RUN mkdir -p /app/storage/receipts

EXPOSE 3000
CMD ["node", "dist/app.js"]
```

## 4. Database Schema

### Entity Relationship Summary

```
Apartment (1)
  ├──▶ Users[]                  (landlord + tenants)
  ├──▶ Rooms[]
  ├──▶ UtilityCharges[]
  ├──▶ ApartmentSubscriptions[]
  ├──▶ Notices[]
  └──▶ Expenses[]

Rooms (1)
  ├──▶ Users?                   (tenant assigned to room)
  ├──▶ Bills[]
  └──▶ Issues[]

Users/Tenant (1)
  ├──▶ Bills[]
  ├──▶ Receipts[]               (tenantId → SetNull on delete)
  ├──▶ Issues[]
  ├──▶ NoticeRead[]             (junction)
  ├──▶ Notifications[]
  └──▶ RefreshTokens[]

Bills (1)
  ├──▶ BillLineItems[]          (snapshot of charges at generation)
  ├──▶ Receipts?                (created after payment)
  └──▶ MpesaTxns[]
```

## 5. API Endpoints

Legend:
- 🔓 = Public (no auth)
- 🔑 = Any authenticated user
- 🏠 = Landlord only
- 🏢 = Tenant only

### Auth

| Method | Endpoint | Access | Body | Description |
|---|---|---|---|---|
| POST | `/auth/register` | 🔓 | fullName, email, phone, password, apartmentName, apartmentAddress | First-time landlord registration. Fails if landlord already exists |
| POST | `/auth/login` | 🔓 | email, password | Returns accessToken + refreshToken + user object |
| POST | `/auth/refresh` | 🔓 | refreshToken | Rotates refresh token, returns new pair |

## 6. Business Logic Rules

### Bill Generation Rules
1. Run `POST /bills/generate` for a given month
2. Find all rooms where `isOccupied = true`
3. For each occupied room, check if a bill already exists for that month (`UNIQUE tenantId + month`) — skip if yes
4. Create bill with:
   - `rentAmount` = room's current `rentAmount` (snapshot — doesn't change if rent updated later)
   - `status` = UNPAID
   - `dueDate` = `rentDueDay`th of the given month
5. For each active `UtilityCharge`, create a `BillLineItem`:
   - FIXED → `amount = charge.amount`, units/rate = null
   - RATE_BASED → `amount = 0` (units not entered yet), `rate = charge.rate` (snapshotted), units = 0
6. Landlord later enters units during meter walk → `PATCH /bills/:id/line-items/:lineItemId` → recalculates `amount = units × rate`

### Bill Total Formula
```
billTotal = rentAmount + SUM(lineItems.amount)
```
**Never stored in the database.** Always computed in the application layer from `BillLineItem` rows.

### Overdue Logic
- A daily cron job runs at midnight
- Finds all bills where `status = UNPAID` AND `dueDate < today - gracePeriodDays`
- Updates them to `status = OVERDUE`
- Sends push notification to landlord for each new overdue bill (if `alertOverdue = true`)

### Tenant Creation Rules
- Only landlord can create tenant accounts
- Selected room must have `isOccupied = false`
- On creation: set `room.isOccupied = true`, `room.leaseStart`, `room.leaseEnd`, `profile.roomId`
- Tenant receives a temporary password — they should change it on first login

### Tenant Removal Rules
- On deletion: set `room.isOccupied = false`, `room.tenantId = null`, `room.leaseStart = null`, `room.leaseEnd = null`
- Tenant profile is deleted (CASCADE deletes their notifications, refresh tokens, notice reads)
- Their bills and receipts are kept for historical records (tenantId goes null via SET NULL)

### Notice Broadcast Logic
- If `tenantId = null`: notice is visible to ALL tenants
- `GET /notices/mine` returns: notices where `tenantId = currentUser.id` OR `tenantId = null`
- `isRead` is computed per-request: check if a `NoticeRead` row exists for this `(noticeId, tenantId)` pair

## 7. Scheduled Jobs

All jobs run inside the Express container using `node-cron`.
Defined in `src/services/scheduler.service.ts`, started when the app boots.

| Job | Cron Schedule | What it does |
|---|---|---|
| Generate monthly bills | `0 8 1 * *` — 1st of month at 8am | Calls generate bills logic for current month for all occupied rooms |
| Mark overdue bills | `0 0 * * *` — midnight daily | Updates UNPAID bills past `dueDate + gracePeriodDays` to OVERDUE. Notifies landlord |
| Rent reminder to tenants | `0 9 * * *` — 9am daily | Sends push to tenants whose bill is due in exactly 3 days |
| Subscription expiry check | `0 9 * * *` — 9am daily | Checks all active `ApartmentSubscription` rows. If `renewalDate ≤ alertDaysBefore days away`, push to landlord |
| Lease expiry check | `0 9 * * *` — 9am daily | Rooms where `leaseEnd ≤ 30 days away`, push to landlord. Only if `alertLease = true` |
| Clean expired refresh tokens | `0 3 * * *` — 3am daily | Delete RefreshToken rows where `expiresAt < now` |

## 9. PDF Receipt Generation

**Tool:** Puppeteer (headless Chromium, installed in Docker image)

**Trigger:** After every successful payment (simulate or real)

**Process:**
1. Payment confirmed → `pdf.service.ts` called asynchronously (non-blocking)
2. Build HTML string with receipt data (tenant, room, bill breakdown, M-Pesa code, receipt number)
3. Puppeteer renders HTML to PDF
4. Save to `/app/storage/receipts/RCP-202504-1A.pdf`
5. Update `receipt.pdfPath` in DB

**File naming:** `RCP-{YYYYMM}-{RoomNumber}.pdf` e.g. `RCP-202504-1A.pdf`

**Serving:** `GET /receipts/:id/pdf` streams the file from disk.
If PDF not yet generated (still processing), returns 202 Accepted — Flutter retries.

## 14. Postman Testing Guide

### Setup
1. Create a Postman collection called **Nyumba API**
2. Create two environments: `Local` and `Production`
3. Set variable `baseUrl` = `http://localhost:3000/api/v1`
4. Create collection variables: `accessToken`, `refreshToken`, `tenantAccessToken`

### Auth Scripts
Add this to the **login request** Tests tab to auto-save tokens:
```javascript
const res = pm.response.json();
pm.collectionVariables.set("accessToken", res.data.accessToken);
pm.collectionVariables.set("refreshToken", res.data.refreshToken);
```

Add this to the **tenant login** Tests tab:
```javascript
const res = pm.response.json();
pm.collectionVariables.set("tenantAccessToken", res.data.accessToken);
```

Use `{{accessToken}}` in the Authorization header for landlord requests.
Use `{{tenantAccessToken}}` for tenant requests.

### Recommended Test Order
```
1.  POST /auth/register               → save landlord tokens
2.  POST /auth/login (landlord)       → verify tokens work
3.  GET  /auth/me                     → verify role=LANDLORD
4.  GET  /apartment                   → verify apartment loaded
5.  GET  /rooms                       → verify rooms exist (0 occupied)
6.  POST /utility-charges             → add Water (RATE_BASED, rate:60)
7.  POST /utility-charges             → add Garbage (FIXED, amount:300)
8.  POST /subscriptions               → add WiFi subscription
9.  POST /tenants                     → create Amina in Room 1A
10. GET  /tenants                     → verify 1 tenant, room occupied
11. POST /bills/generate              → { month: "2025-04" }
12. GET  /bills?month=2025-04        → 1 bill with line items (water=0, garbage=300)
13. PATCH /bills/:id/line-items/:lid  → set units=14 for water line item
14. GET  /bills?month=2025-04        → water amount now 840
15. POST /auth/login (tenant)         → login as Amina, save tenantAccessToken
16. GET  /bills/mine/current          → verify full bill breakdown visible
17. POST /payments/stk-push           → { billId, phone, amount }
18. GET  /payments/status/:id         → poll until SUCCESS
19. GET  /receipts/mine               → verify receipt created
20. GET  /receipts/:id/pdf            → verify PDF downloads
21. POST /notices                     → landlord sends broadcast

23. POST /notices/:id/read            → mark as read
```
